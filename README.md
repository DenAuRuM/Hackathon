# Маршрут — помощник диспетчера

Прототип на JavaScript: независимое ядро планирования, веб-интерфейс, карта, объяснения и перепланирование после срочной заявки. Node.js 20+, без npm-зависимостей и сборщика.

## Запуск

```sh
npm start
```

Откройте http://127.0.0.1:3000. Устанавливать пакеты не требуется. Для другого порта задайте переменную окружения `PORT`. Сервер слушает только локальный компьютер.

```sh
npm test       # автоматические проверки
npm run demo   # пример расчёта и события в консоли
```

Интерфейс загружает `data/demo.json`, позволяет менять веса, импортировать свой JSON, добавлять срочные заявки и скачивать результат. «Построить исходный план» сбрасывает события и пересчитывает исходный набор. Изменение ползунка само по себе не запускает расчёт.

## Алгоритм

Обязательные ограничения проверяются отдельно от оценки. Их нельзя компенсировать весами:

1. У инженера есть требуемый навык.
2. Транспорт соответствует требованию, если оно есть.
3. Начало работы входит во временное окно, включая границы.
4. Путь, ожидание и работа укладываются в смену. Возврат к старту не нужен.

Для каждой заявки перебираются инженеры и **все позиции вставки** в их маршруты. Каждая вставка пересчитывает время всего будущего маршрута, включая ранее назначенные заявки. Среди допустимых вставок выбирается минимальная взвешенная оценка плана. Равные оценки разрешаются порядком инженеров и позиций.

Строятся четыре варианта: сначала заявки с наименьшим числом подходящих инженеров; сначала с ранним окончанием окна; сначала короткие работы; исходный порядок. В первых трёх срочные заявки идут раньше обычных. Пятый кандидат — установленный в условии **базовый алгоритм**: входной порядок заявок, первый допустимый инженер, добавление только в конец маршрута.

Исходные планы сравниваются по числу назначенных заявок, затем числу срочных, затем взвешенной оценке. Поэтому результат не назначает меньше заявок, чем baseline. При перепланировании порядок: **срочные → все назначенные → оценка**. Это позволяет отложить несколько обычных работ ради срочной. Глобальный оптимум не гарантируется; локальный поиск с переносами/обменами и точный решатель не используются.

### Взвешенная оценка

`score = Σ weight[k] × feature[k]`; меньшая оценка лучше. Минимизация итоговой оценки эквивалентна минимизации её прироста при одной вставке.

| Ключ | Признак | Вес |
|---|---|---:|
| `personnel` | Число инженеров с работой | 8 |
| `distance` | Общий пробег / 10 км | 3 |
| `travel` | Время пути / 60 минут | 1 |
| `waiting` | Ожидание окон / 60 минут | 0.5 |
| `balance` | Сумма квадратов долей занятости смен | 0.3 |
| `versatility` | Сумма `(число навыков исполнителя − 1)` по назначениям | 0.5 |
| `stability` | Число старых заявок, поменявших инженера/позицию или утративших назначение | 2 |

Занятость включает путь, ожидание и работу. `versatility` оставляет универсальных исполнителей в резерве, когда работу может выполнить узкий специалист; это не прогноз спроса. `stability` не штрафует сдвиг времени, только инженера, позицию или потерю назначения. Новые заявки штрафа за изменения не имеют.

Нормировка фиксированная: при стандартных весах дополнительный инженер стоит 8 баллов, дополнительные 10 км — 3 балла. Это компромисс, а не строгое правило «любой ценой минимизировать персонал». Для такого предпочтения увеличьте `personnel`, для сокращения расстояний — `distance`. Нулевой вес отключает фактор. Отрицательные, бесконечные и неизвестные веса отклоняются.

`objective` содержит признаки и взвешенные вклады; `alternatives` — оценку и покрытие каждого варианта. Объяснения назначений содержат ограничения и данные о вставке. Они описывают момент решения; последующие вставки могут сдвинуть позицию и время, поэтому финальное расписание объясняется отдельно.

## API

```js
import { plan, baselinePlan, comparePlans, replan, loadJSON } from './src/planner.js';

const data = loadJSON(jsonText);
const result = plan(data, {
  weights: { personnel: 8, distance: 3, waiting: 0.5 },
  roadFactor: 1.25,
  speeds: { 'Автомобиль': 30, 'Пешеход': 5, 'Велосипед': 15, 'Общественный транспорт': 18 },
});
const { baseline, optimized, delta } = comparePlans(data);
// delta = optimized − baseline; отрицательный пробег/персонал означает сокращение.

const updated = replan(result, {
  type: 'urgent_request', time: '10:00',
  request: {
    id: 'urgent-1', location: { lat: 55.753, lon: 37.63 },
    durationMinutes: 40, windowStart: '10:00', windowEnd: '11:30',
    requiredSkill: 'Аварийные работы', requiredTransport: 'Автомобиль',
  },
}, { weights: { stability: 4 } });
```

Функции не изменяют входные данные. `replan` принимает результат `plan`/`replan`, в том числе после JSON-сериализации, и использует сохранённые данные/настройки. Не передавайте вручную изменённый план. Частичные веса дополняются стандартными, при перепланировании — предыдущими значениями.

### Входной JSON

```json
{
  "requests": [{
    "id": "r1", "location": { "lat": 55.75, "lon": 37.61 },
    "durationMinutes": 45, "windowStart": "09:00", "windowEnd": "11:00",
    "priority": "Обычная", "requiredSkill": "Локальные работы",
    "requiredTransport": "Автомобиль"
  }],
  "engineers": [{
    "id": "e1", "name": "Анна", "startLocation": { "lat": 55.74, "lon": 37.62 },
    "shiftStart": "09:00", "shiftEnd": "18:00",
    "skills": ["Локальные работы", "Аварийные работы"], "transport": "Автомобиль"
  }]
}
```

ID — непустые строки, уникальные внутри сущности. Навыки: `Локальные работы`, `Работы на подключение и дозаказы`, `Аварийные работы`. Транспорт: `Автомобиль`, `Пешеход`, `Велосипед`, `Общественный транспорт`. Приоритет: `Обычная` или `Срочная`. `requiredTransport` можно опустить или задать `null`. У инженера 1–3 различных навыка. Координаты и длительность — числа, длительность — целые положительные минуты. Время строго `HH:MM`, `00:00`–`23:59` в пределах одного дня; смены через полночь не поддерживаются.

Интерфейс принимает готовый JSON, source.json, matching.json, enrichment.json и рабочий набор workspace.json. Для исходных CSV из папки «Обезличивание» есть отдельный конвертер, описанный ниже. Адреса без координат нужно предварительно геокодировать. Порядок массива `requests` считается порядком поступления.

### Загрузка south-east.matching.json в интерфейсе

Файл matching содержит соответствия, а не заявки/инженеров. Теперь приложение распознаёт его и загружает `south-east.source.json` из локального репозитория. Район определяется по ID; состав ссылок проверяется против исходного набора. В интерфейсе появятся все 83 заявки, адреса, окна, кандидаты соответствий и недостающие поля. Та же операция доступна через «Данные из CSV → Юго-восток → Открыть набор».

В этих данных всё ещё нет координат, длительностей, приоритетов и характеристик инженеров. Поэтому импорт завершится экраном подготовки, а не вымышленным маршрутом. Предыдущий демо-план очищается; расчёт и события недоступны до заполнения данных. Это состояние не означает, что заявки невыполнимы.

Заполнить недостающие значения можно прямо в JSON-редакторе на странице или загрузить enrichment.json. Для другого компьютера/набора выберите source.json, matching.json и enrichment.json вместе: серверный поиск не потребуется. Смешивание районов и несоответствие ID отклоняются. Кнопка «Скачать рабочий набор» сохраняет source, matching и текущие дополнения одним JSON без потери незавершённой работы. Сохранённый план можно загрузить как исходные данные для нового расчёта дня; это не восстановление фактического выполнения работ.

После обновления кода перезапустите `npm start`: сервер должен знать новые локальные маршруты. Без связанных файлов загрузите source.json вместе с matching.json. Контрольные назначения и отмены автоматически не становятся входом алгоритма.

### Яндекс Карты

В блоке карты выберите «Яндекс Карты», введите ключ JavaScript API и нажмите «Применить карту». Используется официальный JavaScript API v3: схема, метки и линии порядка посещения; координаты передаются в порядке `[долгота, широта]`.

Ключ получают в кабинете Яндекса. Настройте ограничение HTTP Referer для адреса своего приложения по [официальной инструкции](https://yandex.ru/maps-api/docs/js-api/limit.html). Ключ хранится только в памяти страницы, не сохраняется в репозиторий, localStorage или экспорт. Для смены уже использованного ключа обновите страницу. API загружается лишь при выборе Яндекса и наличии ключа; при ошибке/отсутствии ключа выводится объяснение и резервная OSM-карта.

Замена отображения не изменяет расстояния и время пути алгоритма: они по-прежнему оценочные. Геокодирование адресов, дорожные маршруты, пробки и маршрутная матрица — отдельные интеграции, здесь они не реализованы. Условия и доступность API определяются Яндексом; см. [начало работы](https://yandex.com/maps-api/docs/js-api/quickstart.html). Проверить действующий ключ и реальную загрузку Яндекс Карт без пользовательского ключа нельзя.

### Проверка корректности после исправления импорта

Тесты загружают настоящий south-east.matching.json, проверяют 83 заявки, четыре неоднозначные связи, отсутствие придуманных полей, совместную загрузку файлов, экспорт/импорт рабочего набора и отбрасывание чужих районов. Расчёт проверяется на всех 83 исходных окнах с явно тестовыми координатами/нормативами/инженерами, существующими только внутри теста. Это не результат реального распределения Юго-востока.

Отдельная проверка расписания проверяет путь, ожидание, окно начала, конец смены, навыки, транспорт, отсутствие повторных назначений, учёт неназначенных, метрики и сохранение начатых выездов при двух последовательных срочных событиях. Сравниваются стандартные веса и крайние предпочтения персонала/расстояния; исходный план не должен покрывать меньше заявок, чем baseline. Проверяется и переключение карт: порядок координат, обработка отсутствующего ключа/ошибки, уничтожение старой карты и защита от позднего завершения загрузки старого плана. Глобальная оптимальность эвристики не утверждается.

### CSV из папки «Обезличивание»

```sh
npm run import:csv
```

По умолчанию читает соседнюю папку `../Обезличивание` и сохраняет JSON в `data/imported`. Можно указать свой источник и папку результата:

```sh
npm run import:csv -- "путь/к/CSV" "путь/к/результатам"
```

Поддерживаются шесть файлов Востока, Юго-востока и Югоцентра, Windows-1251/UTF-8, разделитель `;`, кавычки и переносы строк в полях. Синтетические заявки и контрольное распределение сохраняются отдельно. Исходные столбцы доступны в `source.raw`; строки офисов вынесены в `offices`. ID заявок — строки с префиксом района; у контрольных записей технический ID дополнительно содержит строку CSV, чтобы не потерять повторный исходный ID.

В источниках 205 синтетических заявок и 205 контрольных записей. Координат, длительностей, приоритетов и полноценного справочника инженеров нет. Эти значения **не выдумываются**. Файлы `*.source.json` — промежуточные данные, их нельзя загрузить как готовый план. `*.enrichment.template.json` содержит null-поля для координат/длительностей/приоритетов и пустой список инженеров; `engineer.template.json` показывает поля одного инженера.

Скопируйте нужный `*.enrichment.template.json` в `*.enrichment.json`, заполните его и соберите вход планировщика:

```sh
npm run prepare:data -- data/imported/east.source.json data/imported/east.enrichment.json data/imported/east.planner.json
```

`locationsByAddress` задаёт `{lat, lon}` по точному адресу, `durationMinutesByTypeHD` — длительности по типу HD, `defaults.priority` — общий приоритет. Для исключений есть `requestOverrides`, ключ — полный ID из source JSON; разрешены location, durationMinutes, priority, requiredSkill и requiredTransport. `engineers` соответствует обычной схеме ядра. Нулевые/некорректные значения не подменяются значениями по умолчанию.

Нужно явно подтвердить, что «Начало/Окончание» означает окно начала работ (`confirmedTimeWindowSemantics: true`): двухчасовой интервал не считается длительностью работы. Транспорт можно указать отдельно для каждой заявки, включая null для отсутствия ограничения, либо подтвердить отсутствие требований по умолчанию (`confirmedNoTransportRequirements: true`). Подтверждения — булевы значения, не строки.

Подготовка не выдаёт частичный набор: если чего-то не хватает, возвращаются причины и итоговый файл не создаётся/не обновляется. В API `preparePlannerData(source, enrichment)` возвращает `{ready, data, issues}`. При `ready: false`, `data` всегда null.

В Юго-восточном контроле повторяется ID `305898293`; обе строки сохранены. Четыре синтетические заявки имеют неоднозначное соответствие контролю. `*.matching.json` содержит кандидатов, найденных по дате, окну, типам, району и адресу без квартиры, а не по порядку строк. Контрольные статусы, отмены и назначения не переносятся в синтетический сценарий. Название бригады не используется как доказательство состава, квалификации или транспорта инженеров.

Повторный импорт обновляет только source/control/matching, пустые *.template.json и отчёт; заполненные *.enrichment.json и *.planner.json не затрагиваются. CSV-оригиналы не изменяются, внешние сервисы не вызываются. Детальный отчёт находится в `data/imported/README.md` и `import-report.json`.

### Результат

- `routes[]`: инженер, старт, `geometry`, упорядоченные `stops`, пробег, время пути, объяснение маршрута. Пустые маршруты тоже возвращаются.
- `stops[]`: ID заявки, координаты, прибытие/начало/окончание (`HH:MM` и минуты от полуночи), отъезд, путь от предыдущей точки, ожидание, `locked`, объяснения.
- `assignments[id]`: `assigned` с инженером и позицией (от нуля) либо `unassigned` с причиной.
- `unassigned[]`: список неназначенных с кодом и русскоязычной причиной.
- `metrics`: количество назначенных/неназначенных, уникальных исполнителей, пробег каждого и всего плана, время пути.
- `changes[]` после события: значения до/после и поля `new`, `status`, `engineer`, `order`, `time`. Изменения относятся к непосредственно предыдущему плану.
- `input`, `options`, `planningTime`: снимок для следующего события; `planningTime` — минуты от полуночи.

Коды причин: `NO_SKILL`, `NO_TRANSPORT`, `TIME_INFEASIBLE`, `NO_CAPACITY`, `PRIORITY_TRADEOFF`. Занятость в выбранном плане не объявляется доказательством невозможности: другое распределение может дать иной результат. Некорректные данные отклоняются с ошибкой вместо молчаливого пропуска.

### Перепланирование

Поддержан обязательный сценарий `urgent_request`. Новая заявка автоматически становится срочной. Время событий не убывает; события можно добавлять последовательно.

Если отъезд **строго раньше** времени события, весь этот выезд фиксируется: инженер, позиция, прибытие, ожидание и работа. Сохраняются выполненные работы, текущая работа и пункт назначения инженера в пути. Ожидание по уже достигнутому адресу также фиксируется. При совпадении отъезда и события сначала применяется событие. Свободный инженер начинает будущий путь не раньше текущего времени и начала смены; занятый — после зафиксированной работы. Истёкшее окно срочной заявки даёт неназначенную заявку, а не путешествие назад во времени.

Метрики относятся ко всему дню, включая выполненные участки. Предполагается исполнение предыдущего плана по расписанию; фактические GPS-позиции, опоздания и прерывание текущей работы не моделируются. Отмена и недоступность инженера пока не реализованы.

## Карта и расстояния

Расстояние — формула гаверсинуса × `roadFactor` (1.25 по умолчанию). Время = `ceil(км / скорость × 60)`. Скорости демонстрационные, не прогноз трафика. Внутренние расстояния не округляются; метрики округлены до сотых, поэтому сумма отображаемых округлённых строк иногда отличается от итога на 0.01 км.

Карта — локальный SVG с проекцией Web Mercator и подложкой OpenStreetMap, охватывающий все точки. Квадраты — старты, цветные кружки — назначения с номером посещения, красные — неназначенные. Наведение показывает подробности. Это обзорная карта без панорамирования и масштабирования; линии соединяют адреса напрямую, а не показывают дорожный маршрут. Подложке нужен интернет; линии и точки доступны без него. Расчёт не обращается к внешним сервисам. При просмотре карты браузер запрашивает OSM-тайлы отображаемого района.

Для промышленного использования потребуется дорожная матрица времени/расстояний и соблюдение [политики тайлов OpenStreetMap](https://operations.osmfoundation.org/policies/tiles/). В MVP нет предзагружения или массового скачивания тайлов.

## Проверки и границы

Тесты проверяют ограничения, границы окон/смен, ожидание и путь, вставку перед работой, влияние весов, базовый алгоритм, срочность, сохранение начатых выездов, повторные события, сериализацию, некорректные данные и детерминизм. Ещё 40 сгенерированных наборов проходят независимую проверку расписания и сравнение покрытия с baseline.

Демо: baseline назначает 6 из 8 заявок двум инженерам с пробегом 13.95 км. Эвристика назначает те же 6 заявок двум инженерам с пробегом 10.44 км. Две невыполнимые заявки оставлены специально: неподходящий транспорт и поздняя длительная работа. После демо-события в 10:00 назначено 7 из 9, пробег 12.51 км.

Ядро рассчитано на небольшие демонстрационные наборы, а не тысячи заявок: каждая вставка пересчитывает маршрут и оценку. Возможные улучшения — дорожная матрица, локальные переносы/обмены и Web Worker для больших наборов.
